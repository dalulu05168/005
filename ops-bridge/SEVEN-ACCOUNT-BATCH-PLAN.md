# Nuvexa Ops｜7座位全天顺序滑动调度规范（待实现）

## 用户确定的模式

提前提供一整天需要转发的角色及账号顺序（可附计划时间）。Telegram 实际收到获授权来源群的三行格式信息后，才依顺序进行真实 WhatsApp 转发。角色编号与身份取后台当前配置，编码唯一。

**7座位是一组始终最多7个不同的真实活动 WhatsApp Web 会话，不是每7个全部完成再整体更换，更不是7条消息并发发送。**

- 首先按全天顺序逐个恢复最多7个不同的已授权发送账号，限制同时在线浏览器资源。
- 一个账号完成当前轮所有目标群组的真实发送确认（ACK），且该账号没有在发送或待核实任务时，只释放这一个账号的浏览器资源，其他6个座位继续使用。
- 空出一个座位后立即从全天计划挑选**下一位尚未占座的实际发送账号**启动并预热，完成“一个下、一个上”的连续滑动。
- 如果下一个角色绑定的物理账号已经占座，直接复用它，不重复占座。一个真实发送号可能绑定多个角色编号，但不能冒充多个独立人；同一账号一天内反复出现可离座后再从保存的会话恢复。
- 不一定占满7个座位；实际参与账号少于7个时运行少于7个。只有3或5个稳定资源时可以调低上限。
- 普通消息维持原始顺序；助理/教授的已到达合法消息允许在**当前已开始任务完成后**跳过尚未开始的普通待执行消息，但不能打断SENDING/VERIFYING、跳过未核实结果或凭计划虚构发送内容。

## 助理和教授的优先插队（新确定的例外）

助理1号、教授1号使用频率高，均视为**同等级最高优先角色**。建议尽量将这两个真实授权账号预热并长期占用优先座位（默认2席），其余最多5席滚动；若某一优先账号尚未占座而7席全满，则等待一个普通账号已完成/可安全释放，再抢先将助理或教授补入。没有空位或所有账号正在发送/待核实时不能强行踢人、不能临时超过7席。

**消息插队也是有效的，但只能在任务边界发生**：
- 仍须实际收到符合三行格式和来源权限的助理或教授信息；不能仅凭全天计划虚构一条消息。
- 当前**已开始执行**的普通任务及其所有目标群组必须完成确认后才能切换；SENDING 和 VERIFYING 的消息绝不被打断。
- 对尚未开始发送的普通待执行消息，助理和教授的已到达消息有更高优先级，二者之间按实际到达先后顺序，普通消息之间也保留原来先后次序。
- 这是一项明确的**优先例外**：普通消息的实际发送顺序可能晚于比它后到的助理、教授消息；显示计划与实际执行进度时需要明确区分，不可称为全局绝对FIFO。
- 常驻优先席位只提高恢复/切换效率，不能意味着强制连续发言、跳过合法限制或对发送成功作假。
- 若助理1号/教授1号被确认不可用，仍分别由助理2号/教授2号专属备用换入，不将普通备用号用于代替。
- 管理端应提供启用/暂停优先调度、查看当前优先消息和正在保护的普通任务；普通队列不能在长时间优先消息时被无限饿死，实际频率需在试运行时观察并设置公平性阈值。

**开发现状**：后端已经加入 *仅在安全边界优先选取已采集到的助理/教授任务* 的隔离分支逻辑和纯座位选择规则；7席实际调度、单账号优雅关闭和真实发送端仍未实现并验收。

## 一天计划示例

预设的发言顺序：助理 → 45老男 → 12新女 → 教授 → 51新男 → 37老男 → 06老女 → 22新女 → 31老男 → … 。

启动时优先准备上面前7位实际不同的发送账号；45完成其当前轮全部目标群组的确认后，只释放45的会话并把下一位22补到这个空座。其它6个不需要等待45所在“整批”全部完成。若计划之后再次出现45，它可从本地保存的授权会话重新入座。

## 执行状态机

1. PLAN：上传/编辑全天角色顺序及可选预计时间；逐项检查人物编号、身份、真实账号绑定及已授权的Telegram来源和目标群组；计划未执行部分允许调整。
2. WARM：对当前轮需要的最多7个不同物理发送账号逐个启动浏览器，不做同时7实例冷启动的资源冲击。必须等WhatsApp ready＋getState CONNECTED才认为已在线。
3. SEND：仅当原始消息在Telegram实际到达、与预定顺序和当前绑定身份匹配时，交给全局严格顺序队列；目标群组按既定顺序进行投递和回执核实。
4. ACK_AND_RELEASE_ONE：发送端回执必须匹配实际账号ID、群组ID、WhatsApp消息ID及provider ACK；该账号在本轮所有目标群已完成，并且没有SENDING/VERIFYING时，才允许关闭这个账号的client。
5. FILL_ONE：确认一个浏览器实例已经安全销毁释放资源，接着将下一位未占座账号入座预热。不得等待整批，也不能超出活动座位上限7个。
6. PAUSE_ON_AMBIGUITY：如账号掉线、未授权、Telegram消息未到、角色编号或身份错误、发送结果未知或正在VERIFYING，则暂停相关执行/当前队列头，不越过、不虚报成功、不盲目重发。需要备用账号时按助理2、教授2及普通备用1→2→3的既定规则按需占座换入。
7. FINISH：全天任务均已确认完成后安全释放活动浏览器会话，保留授权会话、人物绑定与群组配置供次日恢复。已完成的聊天内容、图片引用及任务明细立即清理，只保留短时去重哈希。

## 座位UI与颜色

- 7个席位显示真实账号标识、对应角色、真实在线绿点、计划休眠灰点、意外离线红点，以及预热/发送/待核实/释放等状态。
- 附全天任务序列、当前执行角色、下一位补位候选、已完成数与等待数；这不等于保存消息正文和历史聊天内容。
- 会话释放时**不可执行WhatsApp logout、不可删除LocalAuth资料**；计划睡眠不可显示为真实在线。真实账号再次上座时可尝试免扫码恢复，但失效后仍可能需要账号持有人重新授权。
- 前7个并非一组同时发送。按原有全局严格顺序执行；不保证7倍吞吐。

## 研发与性能验收状态

- 当前 Windows WhatsApp 连接器默认最多3个会话；虽然可配置到7，但**单账号优雅卸载/自动补座、全天计划调度、实际WhatsApp自动发送Worker都尚未实现或联调验收**。
- 后续实现应增加：按账号的stopSession/release API、仅恢复当前座位账号的会话选择机制、全天顺序调度和进度状态、与严格任务队列的无重复投递对接、恢复和异常处理。
- 先按3、5、7会话逐级做真实压力测试，记录内存、CPU、登录恢复时间、逐个补座耗时、断线/未知回执及群组发送确认，不合格不能对外宣布完成。
- 只用于获得账号持有人授权的真实业务消息，不能以虚构的独立投资者身份制造虚假市场共识、交易表现或收益。
- 本规范仅写入独立开发分支，未合并、未发布生产，不修改admin.nuvexapro.com、主域名或现有账号资料。
